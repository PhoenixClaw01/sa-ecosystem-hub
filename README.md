# sa-ecosystem-hub

A public, signed record of updates for [sa-ecosystem-node](https://github.com/PhoenixClaw01/sa-ecosystem-node), a read-only community MCP node inspired by Star Atlas.

This repository holds only signed JSON files and a manifest. It holds no signing keys, no node source code, no payment details and no personal data. Any node can pin a commit of this repository and serve what it holds through its MCP tools (`hub_updates`, `list_listings`, `search_hub`, `claim_status`, `player_story` and more; 22 tools in all on node main) and the plain view at `/plain/`.

This is an unofficial community project. It is not affiliated with ATMTA, holds no funds, and never handles payment.

Maintained by **Phoenix Collective (Falkor's team)**. Governance for this hub and its signers is public at [PhoenixClaw01/phoenix-gate](https://github.com/PhoenixClaw01/phoenix-gate).

Hub id: `https://github.com/phoenixclaw01/sa-ecosystem-hub` (repository `PhoenixClaw01/sa-ecosystem-hub`; this normalized URL is what story opt-ins sign).

## What lives here

| Path | What it is |
|---|---|
| `hub-manifest.json` | The ordered list of signed update files a node reads. A node pins this file's sha256 hash. |
| `updates/` | One signed hub update per file, named `<id>.json`. Only signers add files here. |
| `proposals/` | Unsigned proposals sent by pull request. A signer reviews each one and, if accepted, signs it into `updates/`. Nodes never read this folder. |
| `VERIFY.md` | The exact verification rules, generated by the node's `hub-store-init` tool. |
| `CONTRIBUTING.md` | How to send a proposal, and how to run your own node and hub. |

## How updates work

Every update is one JSON document with three parts: `payload`, `signature` and `approvals`.

- The **author** signs the payload. The author must be on the signer list that the reading node trusts.
- **Approvers** sign the payload's hash. A node serves an update only when enough distinct trusted keys have approved it (the node's approval threshold).
- Each update points at the previous one (`prev`), so the record is a single chain. A changed file, an unknown signer, a repeated id or a manifest that does not match the pinned hash is not served.

Signatures are detached ed25519 over fixed text. A node checks a key made with the node's `hub-keygen` (an **agent record key**, which holds no funds) and a wallet's `signMessage` signature the same way. They are not transactions, they move no funds, and they grant no access to anything.

**Today:** the Phoenix Collective node uses threshold 2 and counts the author's own approval. Listings and guilds are authored by the Phoenix Collective agent record key (`G2Ph…`) and approved by Falkor's wallet (`FC1e…`). The GaliaMeta DAC wallet (`EU7z…`) is on the allowlist and has not signed anything.

**Planned:** agent record keys sign everyday records (listings, guilds) and a second Phoenix agent key replaces the wallet approval there. A player's own wallet signs only that player's records (story opt-ins, player claims). Until that migration lands, any allowlisted key can approve any record.

## Listings

A `listing` update describes a business, project, guild or community link: a stream (`referral`, `hybrid`, `irl` or `player`), a category, a title, an owner name, the owner's own public `https` page, a status, an as-of date and an expiry no more than 90 days later.

- A `referral` listing must carry a plain disclosure.
- Listings expire. An expired listing is hidden unless a caller asks for expired rows, and it is then marked expired.
- Nodes show the URL as given. They never take payment and never proxy a checkout.

### Listing and guild records (node main `9c71cf6`)

- **Listing** (kind `listing`): stream `referral`, `hybrid`, `irl` or `player`; status `available`, `sold_out`, `inquire_only`, `paused` or `withdrawn` (a takedown). Optional `listingId` (the stable identity; set it on every new listing) and optional `image { url, alt, link? }`.
- **Guild** (kind `guild`): `name`, `description` (up to 280 characters), up to 8 `https` `links`, and optionally `tags`, `image`, `site`, a `discord` invite (`discord.gg` or `discord.com/invite` only) and `withdrawn: true`. No member lists, wallets or prices.
- **Images:** a logo committed to this repository (for example `images/<name>.png`) is what `/plain/` shows, loaded from `raw.githubusercontent.com` at the pinned commit. An external `https` logo stays valid in the signed record but the page does not load it. No SVG.
- **Search:** `/plain/` and the `search_hub` tool search listing names, guilds, businesses, tags and short descriptions. Players appear only after they opt in.
- Exact rules are in `VERIFY.md`.

### Launch drafts

52 drafts are prepared for launch-day signing: **24 business and creator listings** and **28 guilds**, each written from that project's own public words, links and logo. Nothing is published until it is signed at threshold 2 (below).

### Curator listings

Phoenix Collective (Falkor's team) may sign curator listings for other projects, businesses and guilds, so nobody has to add themselves. A curator listing uses only that project's own public links and public logos. It does not use our own wording about them, and it does not claim that the project signed it or endorses us. Each curator listing says so in its `ownershipProof` note (`signer_review`).

## Claim your listing (self-claim)

If you run a listed project, guild or business, or you are a player, you can claim your listing with your own wallet. A claim is a **signed claim record**: your wallet signs a short fixed message (`signMessage`, not a transaction; it moves nothing) that binds that wallet to one listing or guild on this hub. Today every claim, including guild and business claims, is wallet-signed. **Proposed, not built:** guilds and businesses may claim with an agent record key instead, since most businesses have no wallet.

- **Players** are checked automatically against their on-chain Star Atlas **Player Profile**: the claim goes active when the wallet is a current key on that profile.
- **Guilds and businesses** go active when a hub curator **countersigns** the claim.
- **Discord and X** proof is optional. Each node operator decides whether to verify it. A verified attestation is a signed record in this hub, so it is **portable**: every node that trusts the same verifier shows the same badge.
- Once a claim is active, your own signed updates for that identity win: logo, links, site, Discord invite, description, or a takedown. You cannot change anyone else's listing, the signer list or the threshold.
- `/plain/` shows a `claimed` badge (no wallet address). The `claim_status` MCP tool shows where any claim stands.

Full steps: `CONTRIBUTING.md`, and `docs/claim-and-verify.md` in the node repository.

**Fix-or-remove rule.** A curator listing that is flagged (a dead invite, a missing description, wording that breaks the listing rules) is fixed by its owner through self-claim, or it is removed. Removal is a signed `withdrawn` update. You can also ask for removal at any time by opening an issue here or emailing support@phoenix-collective.app, with no questions asked.

## Story opt-ins and revocations

The node's `player_story` tool tells a player's public story only after that player opts in.

- **Opt in.** The player's own wallet signs one fixed sentence that names this hub:
  `I allow sa-ecosystem-node to tell my public Star Atlas story. Wallet: <address>. Date: <YYYY-MM-DD>. Hub: https://github.com/phoenixclaw01/sa-ecosystem-hub. Links: yes.` (or `Links: no.` to keep explorer links out).
- **Revoke.** The player signs:
  `I revoke sa-ecosystem-node from telling my public Star Atlas story. Wallet: <address>. Date: <YYYY-MM-DD>. Hub: https://github.com/phoenixclaw01/sa-ecosystem-hub.`
- A hub signer publishes that signature as a `story-optin` update. The signer cannot change the sentence, the hub or the links choice.
- A revoke wins over any allow dated the same day or earlier. Replaying an old allow does not undo a revoke.
- A signature that names a different hub does not count here.

There is no separate opt-in database. This repository is the whole record.

## Signer changes and revoking a signer

- A `signer-change` update adds or removes one key in a named signer set. The other members of that set must approve it, and the author's own approval never counts. It applies only to later links in the chain, so earlier records stay valid.
- Each node operator can also ignore a signer locally (`HUB_REVOKED_SIGNERS`) without waiting for a new commit here. **This is retroactive:** if a revoked key approved a record that still needs it to meet the threshold, that record and every later record in the chain are rejected on that node. Re-approve those records with another key first, or use a `signer-change`.
- Every listing expires within 90 days unless it is re-signed.

## What a signature means

When a node shows a listing, it shows who signed it and this line:

> Signed by <signer>. This signature means that signer published this listing. It does not move money, and this node never handles payment.

A signature means the named signer published that exact text. On a curator listing it also means Phoenix Collective checked that the link goes where it says on the as-of date. It does not mean the listed project signed it, endorses anyone, or guarantees anything. Check the owner's own page before you act.

## Verify it yourself

See `VERIFY.md`. In short: check out the pinned commit, run `sha256sum hub-manifest.json`, and compare both to the node's `HUB_GIT_COMMIT` and `HUB_STORE_MANIFEST_HASH`. Then check each signature against the signer list.
